# Protected Slides unlock

The [Chromium 158 profile](../results/2026/11-10/supabase-current-chromium.md) reached all four final application assertions. Every failed GET matched the protected iframe artifact in the second Slides publication snapshot. Each failure was `net::ERR_ABORTED` during the password gate, with no retained response.

The unlock Server Action writes the signed access cookie after verifying the password. Next.js 16.1.6 marks the route for rerender after a cookie mutation, synchronizes the changed cookies for that render and applies the returned route data on the client. The protected page reads that cookie before returning the iframe. The client also issued a hard reload when the action returned successfully. The reload could interrupt a just-mounted iframe. The old run did not retain enough request context to establish that sequence. [Cookie mutation source](https://github.com/vercel/next.js/blob/v16.1.6/packages/next/src/server/web/spec-extension/adapters/request-cookies.ts#L106-L120) · [Server Action render](https://github.com/vercel/next.js/blob/v16.1.6/packages/next/src/server/app-render/action-handler.ts#L1124-L1154) · [Client route update](https://github.com/vercel/next.js/blob/v16.1.6/packages/next/src/client/components/router-reducer/reducers/server-action-reducer.ts#L352-L410)

Remove the forced reload and let the action's render update the page. If the owner removes protection while a visitor has the old gate open, the action requests a refresh without issuing a cookie. A focused unit check covers that branch alongside the six existing access checks. Run the four existing journeys against the same production build profile, frozen lock and browser toolchain. Keep every browser assertion, request-failure count, private access check, two Next-only TLS windows, fixture scope and teardown check. The controller binds the browser's reported initial version IDs to the seeded fixture, in addition to its existing workspace, deck and public IDs. [Next.js refresh implementation](https://github.com/vercel/next.js/blob/v16.1.6/packages/next/src/server/web/spec-extension/revalidate.ts#L53-L75)

The password gate component and unlock action are the only changes among the 286 previous application inputs. The focused unit file and its existing Vitest configuration are two additional verification inputs. The previous Chromium 158 report is pinned by byte count and SHA-256. The four failed journeys remain in the record. The check uses the same disposable Supabase stack in one public 20-minute Ubuntu runner with authored data.
